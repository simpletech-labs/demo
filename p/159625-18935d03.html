<프로젝트 진단>
이 공고의 평가 지점은 화면이 아니라 재현성입니다. 공고에 두 문장이 못 박혀 있습니다. 항생제 추천 알고리즘은 변경하지 않는다, 결과물은 별도로 선정한 독립 기술검증 업체가 검수한다. 여기에 목표가 하나 더 붙습니다. 발주자가 AI 도구로 소규모 변경→자동시험→Preview 배포→이전 버전 복구를 직접 하는 것입니다. 정리하면 ①권한이 실제로 막히는지 ②같은 입력에 같은 결과가 나오는지 ③검수자가 문서만 보고 환경을 다시 세울 수 있는지, 이 세 가지가 완료 조건입니다. 기존 MVP는 동작하지만 이 세 가지를 증명할 장치가 없습니다. 20일 중 3일을 코드 인수와 문서화에 먼저 쓰는 이유입니다.

<작업 범위>
A안(기본) — ①인증·권한: 의료진 로그인·로그아웃, 관리자·일반 사용자 구분, 계정 관리, 사용자별 임상 검토 기록 접근 제한. ②접근통제 시험: API별 인증 확인, Supabase RLS 정책 적용(사용자·기관 단위), 파일 저장소 권한, 로그인·DB·파일 접근을 실제 시험으로 확인한 결과표. ③환경 분리: 개발·테스트·운영 분리, GitHub Actions 자동 빌드·타입 검사·핵심 자동시험, Vercel Preview 배포, 운영 배포 전 승인 절차, 환경변수·비밀키 관리, 이전 정상 버전 복구 절차와 실제 복구 검증. ④Claude Code 개발체계: 프로젝트 설정과 규칙 문서(변경 금지 영역·임상 로직 보호·파일별 작업 범위), AI 생성 코드의 자동시험·검토·승인 절차, 승인 없는 운영 반영 차단. ⑤인수인계: 비전공자용 단계별 매뉴얼과 발주자 실습(코드 변경→자동시험→Preview 배포→복구) 1회, 실습 중 막히는 지점 보완.
B안(최소 파일럿) — 기존 비식별·합성 증례 DB 저장·재조회 안정화, 사용자별 증례 기록 생성·조회, UTI·폐렴 입력→OCR 확인→추천 결과 조회 흐름 개선, 저장 입력정보와 추천 결과 일관성 검증. 새 관리 시스템을 만들지 않고 기존 구현과 DB 구조를 재사용합니다.
기술 스택 — Next.js·TypeScript·Supabase(PostgreSQL)·Vercel·GitHub를 그대로 유지합니다. 기존 코드를 갈아엎지 않는 것이 검수 리스크를 가장 줄이는 선택입니다. 추가로 GitHub Actions, Playwright 기반 핵심 화면 자동시험, Claude Code용 규칙 문서(CLAUDE.md)를 붙입니다.

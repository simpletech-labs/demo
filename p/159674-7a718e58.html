<프로젝트 진단>
이 서비스에서 사고가 나는 지점은 기능 수가 아니라 "견적과 확정 금액이 다를 때"입니다. 신청 시 무게를 받지 않기로 한 이상 금액 차이는 예외가 아니라 정상 흐름입니다. 그런데 대부분의 구현은 이 차이를 예외 처리로 밀어두고, 현장에서 기사가 구두로 설명하고 결제는 나중에 되지 않는 구조가 됩니다. 저희는 이 흐름을 정상 경로로 승격시킵니다.
첫째, 견적 화면에 단일 금액이 아니라 "예상 범위"를 표기합니다. 최종 금액은 현장 확인 후 확정된다는 문장을 견적 화면과 예약 확인 화면에 고정합니다. 둘째, 기사가 현장에서 추가 사유를 자유 입력이 아닌 코드로 고릅니다(엘리베이터 없음, 주차 불가, 미고지 품목, 규격 초과). 코드를 고르면 앱이 변경 금액과 사유를 계산해 고객 화면에 즉시 띄웁니다. 셋째, 고객이 앱에서 확인하고 동의해야 결제가 진행됩니다. 동의가 없으면 결제를 걸지 않고 '보류' 상태로 두어 운영자 협의 큐로 보냅니다. 넷째, 동의 이력(금액·사유·시각·동의 방식)을 모두 남겨 분쟁 시 근거로 씁니다.
두 번째 판단은 확장 구조입니다. 봉투 수거는 요금 기준이 무게가 아니라 봉투 수량·정기 구독이라 지금과 계산 방식이 다릅니다. 그래서 신청 데이터에 서비스 종류를 두고, 진행 단계(요청→견적→예약→배정→수거→확정→결제)를 서비스 종류와 분리합니다. 요금은 규칙을 코드에 박지 않고 요금 규칙 테이블로 뽑아, 봉투 수거를 붙일 때 새 화면이 아니라 새 규칙만 추가하면 되게 만듭니다.

3) 고객 앱: 문자 인증·카카오/애플/네이버 로그인, 주소 관리와 서비스 지역 판별, 사진 첨부 견적 요청, 견적 확인·예약, 진행 상태와 수거 사진 확인, 카드 등록 후 자동 결제, 영수증, 공지·FAQ·1:1 문의·카카오 상담 연결.
4) 기사 앱: 당일 목록, 지도·길찾기 연결, 도착·완료 체크, 수거 사진, 특이사항 등록, 무게 입력과 요금 자동 계산, 추가 비용 사유 선택.

기술 선택(비개발자용 설명)
고객 앱과 기사 앱은 React Native(Expo) 한 벌의 코드로 iOS·Android를 함께 냅니다. 두 앱을 따로 만들면 같은 기능을 두 번 만들고 두 번 고쳐야 해서, 유지보수 비용이 두 배가 됩니다. 관리자 웹은 Next.js, 서버는 NestJS, DB는 PostgreSQL입니다. 결제는 국내 PG의 빌링(정기결제) API를 쓰고, 알림은 카카오 알림톡과 문자를 함께 붙입니다. 사내에 개발 인력이 없으시니, 국내에서 인력 구하기 쉽고 문서가 많은 스택으로 골랐습니다. 나중에 다른 개발사에 맡기더라도 이어받기 쉬운 조합입니다.

1) PG 빌링 심사는 보통 2~3주, 알림톡 템플릿 심사는 3~5영업일 걸립니다. 발주사 명의 신청이므로 착수 첫 주에 서류 목록과 순서를 정리해 드리고, 심사 전에는 테스트 키로 개발합니다.
2) 위치기반서비스사업 신고가 늦으면 앱 출시가 막힙니다. 스토어 제출 전에 완료를 조건으로 잡고, 2주 차에 진행 상태를 점검합니다.

<기대 결과>
완료 시점에 대표님이 하실 일은 견적 작성과 기사 배정, 그리고 예외 건 협의뿐입니다. 신청·일정·결제는 앱에서 끝나고, 금액이 달라진 건은 고객 동의 이력이 남아 있어 다툼이 생기지 않습니다. 구조가 서비스 종류와 분리되어 있으므로 봉투 수거를 붙일 때 다시 만들지 않고 요금 규칙과 신청 유형만 추가하면 됩니다.

<확인이 필요한 질문>
1. 무게 요금은 구간형(예: 100kg까지 3만원)인지 kg당 단가인지 알려주세요. 규칙 테이블 설계가 여기서 갈립니다.

3. 수거 당일 취소·노쇼 정책(위약금)이 정해져 있나요? 결제 흐름에 직접 영향을 줍니다.
4. 기사는 직원인가요, 위탁인가요? 위탁이면 기사 앱에 정산 화면이 필요해 범위가 달라집니다.

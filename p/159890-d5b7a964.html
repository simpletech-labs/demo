<사전 질문>
확인되면 바로 범위를 확정할 수 있는 네 가지만 먼저 여쭙습니다. ①캠퍼스별 엑셀 수강생대장 양식이 통일되어 있나요? 실파일 1부를 보면 이관 공수를 정확히 산정할 수 있습니다. ②반·과정·수강료 체계가 캠퍼스마다 다른가요? ③결제선생 가맹점 계정과 정산 주기, 취소·환불 규정, 알림톡 발송 대행사는 정해져 있나요? ④통장 입금 배정 권한은 본사와 캠퍼스 중 어디에 있나요?

<프로젝트 진단>
어려운 지점은 화면 39장이 아니라 관계 구조와 금액입니다. 학생 한 명이 여러 과목을 듣고 형제가 함께 다니며 보호자가 두 명인 경우까지 겹치는데, 이를 엑셀 한 줄로 관리하면 청구가 어긋납니다. 청구·납부·미납이 엑셀, 종이 양식, 결제서비스, 계좌이체, 현장 카드로 흩어져 있으면 월마감에서 합이 맞지 않고, 그 불일치가 곧 학부모 민원이 됩니다. 그래서 학생–수강(과목)–청구–납부를 1:N으로 분리한 기준정보를 먼저 세우고, 선생님이 입력한 수업 기록이 출석부·보고서·청구의 단일 원천이 되게 설계합니다. 권한은 5개 역할과 캠퍼스 두 축으로 나누되, 캠퍼스 분기는 코드 분기가 아니라 데이터 필터로 처리해 8곳을 한 벌로 운영합니다. 시안 39장은 선생님 10·원장 13·본사 6·학부모 6·학생 4로 역할이 이미 갈려 있어, 이 경계를 그대로 권한 경계로 쓰면 화면과 권한이 어긋날 여지가 줄어듭니다.

<작업 범위>
진행 — ①5개 역할·캠퍼스별 권한 제어와 로그인(밝은/어두운 모드, 접속·변경 로그, 개인정보 암호화, 주민등록번호 미수집) ②수업 기록 기반 출석부·업무일지·주간 보고 자동 생성과 A4 인쇄 ③수강생대장의 월별 청구·납부·통장 입금 배정·미납 알림·청구서 발송 ④결제선생 연동과 수납·정산 대조(결제 취소·환불·현금영수증 포함) ⑤카카오 알림톡 발송과 실패 시 문자 대체. 여기에 반·전체 시간표(강의실 배정, 겹침 표시, 자동 생성), 상담 기록과 수강 전환, 서류 발급, 엑셀 내보내기, 기존 자료 이관, 휴대전화 반응형을 포함합니다. 인쇄는 A4 규격으로 고정하고, 수강생대장은 엑셀로 내보내되 본사와 원장의 조회 범위를 넘지 않게 권한을 검사합니다. 브라우저는 PC 크롬·엣지, 모바일 크롬·사파리를 기준으로 검증합니다. 구현은 Spring 기반 API와 MariaDB, 알림 발송 큐는 Redis, 배포는 Docker·GitHub Actions로 구성합니다.
제외 — 학원 소개 홈페이지(공고상 분리 견적), 회계 전표 자동 생성, 양식이 확정되지 않은 교육청 점검 서류 일부. 5,000만 원 안에서 1·2단계를 완결하고 3단계 서류 종수를 예산에 맞춰 조정하는 순서를 제안합니다.
경험 근거 — 월별 미수금 자동 생성은 Spring Scheduler로 구현해 운영했고, 다중 워크스페이스 권한·승인 프로세스, 관리자 화면 기획부터 운영, 키즈노트 알림장·공지·투표·다국어 운영, WebView·반응형 화면은 직장에서 맡아온 범위입니다.

<실행 플랜>
D1–D25 요구사항과 기준정보 확정(캠퍼스별 용어 차이, 청구 규칙, 이관 양식 검증). 게이트1 — 요구사항 정의서·화면 목록·기준정보 승인.
D26–D70 1단계. 권한·로그인, 수업 기록, 자동 양식 생성, 학부모·학생 화면(결제 제외), 원장 기본 화면. 게이트2 — 캠퍼스 1곳 2주 시범 운영, 출석부·업무일지가 수기 양식과 동일한지 대조.
D71–D110 2단계. 수강생대장·수납, 결제선생·알림톡 연동, 학부모 결제, 본사 수납관리. 게이트3 — 시범 2곳에서 실제 청구 1회차를 청구→납부→미납→정산 대조까지 완주.
D111–D135 3단계. 본사 화면, 전체·자동 시간표, 서류 발급, 자료 이관. 게이트4 — 2곳 병행 운영 후 전체 8곳 확대.
D136–D150 안정화, 운영 교육, 인수인계.
단계마다 앞 게이트 승인 후 착수합니다. 공고가 요구한 '단계별 한 캠퍼스 시범 후 전체 확대'를 그대로 일정에 박아 두어, 검증되지 않은 화면이 8곳에 동시에 깔리는 상황을 막습니다. 검토 의견은 3영업일 안에 반영합니다.

<리스크와 대응>
금액 오류 — 결제선생 응답과 내부 청구를 금액·건수로 매일 대사하는 배치를 두고, 차액이 나면 원인을 추적하는 화면을 만듭니다. 금액은 원 단위 정수로만 계산하고, 취소·환불은 상태 전이를 한 방향으로 고정해 중복 처리를 막습니다. 결제선생은 직접 연동한 경험이 없어, 올더게이트·PayAt 연동에서 다뤄온 결제·취소·환불 처리 방식과 승인·정산 대사 절차를 기준으로 설계하겠습니다.
연동 일정 — 결제선생 API 스펙과 알림톡 템플릿 승인은 외부 일정이라 D26 전에 착수합니다. 늦어지면 1단계를 먼저 출시하고 2단계에서 붙입니다.
전환 저항 — 8곳을 동시에 바꾸지 않습니다. 신규 입력만 새 시스템으로 받고 기존 장부는 읽기 전용으로 병행해 현장 부담을 줄입니다.
이관 품질 — 양식이 캠퍼스마다 다르면 이관이 곧 개발이 되므로 D25 안에 실파일로 검증하고, 이관 후 건수·금액 검증 결과를 문서로 남깁니다.
개인정보 — 미성년 학생과 보호자 정보를 다루므로 역할·캠퍼스 단위 접근 제어, 변경 이력 로그, 일 단위 자동 백업과 복구 절차를 1단계부터 넣습니다. 주민등록번호는 수집하지 않는 전제로 화면과 DB를 함께 설계합니다.

<기대 결과>
1. 수업 기록을 한 번 입력하면 출석부·업무일지·주간 보고가 생성·인쇄되어 수기 작성이 사라진다.
2. 원장이 수강생대장 한 화면에서 청구·납부·미납 알림을 처리하고, 통장 입금 배정까지 끝나면 미납생이 자동으로 추려진다.
3. 본사가 8개 캠퍼스 수납과 정산 대조 결과를 한 화면에서 확인하고, 손으로 맞추던 월마감이 시스템 숫자를 확인하는 일로 바뀐다.
4. 결제선생 결제 건과 내부 청구의 금액·건수 대사 차이가 0건이다.
5. 알림톡 실패 건이 문자로 대체 발송되어 결제·출결 안내 누락이 0건이다.

관련 업무 경험 (외주 실적 아님 — 직장 수행 업무)

  • 올더게이트(온라인)·PayAt(오프라인) 결제모듈 연동과 결제·취소·환불 처리, ERP 연동을 맡았습니다.
  • MSSQL 기반 ERP와 일 단위 데이터 연동 구조를 설계·운영했고, 주문·재고 데이터를 양방향으로 맞췄습니다.

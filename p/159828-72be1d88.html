<프로젝트 진단>
공고에 표시된 기술 목록이 이 과업의 성격을 거의 정합니다. 객체 탐지·이미지 세그멘테이션·OpenCV 가 함께 있고, FAISS·벡터 DB 와 FastAPI·React·PostgreSQL 이 같이 있습니다. 즉 ① 현장에서 찍힌 이미지나 계량값을 모델로 판독하고 ② 과거 실적과의 유사도로 "이번 건이 평소와 다른가"를 판정하고 ③ 그 결과를 웹 대시보드에서 사람이 확인하는 구조입니다. 문제는 대부분 세 번째에서 생깁니다. 탐지 모델만 잘 만들어도, 판정 기준이 담당자마다 다르면 알림은 소음이 되고 아무도 보지 않게 됩니다. 그래서 이 견적은 모델 정확도보다 "판정 기준을 문서화하고, 알림이 실제로 처리되는 흐름"에 공수를 더 배분했습니다.
150일은 모델 개발만 보면 넉넉하고, 데이터 라벨링과 현장 검증까지 넣으면 빠듯한 기간입니다. 라벨 정의를 2주 안에 확정하지 못하면 뒤 일정이 그대로 밀리므로, 첫 산출물을 라벨 정의서로 잡았습니다.

3. 이상탐지 — 규칙 기반 임계값과 통계적 이상탐지를 먼저 세우고, 데이터가 쌓인 뒤 모델 판정을 결합합니다. 초기부터 딥러닝 단독 판정으로 가면 근거 설명이 안 됩니다.
4. 유사 사례 검색 — 과거 실적을 벡터로 색인해 "비슷한 건은 어떻게 처리됐는지"를 담당자 화면에 함께 보여줍니다.
5. API·DB — FastAPI, PostgreSQL, 배치·재학습 파이프라인, 모델 버전 관리.
6. 대시보드 — 실적 추이, 이상 건 목록, 건별 상세(원본 이미지·판정 근거·처리 이력), 알림 설정.
7. 운영 이관 — 재학습 절차, 임계값 조정 가이드, 관리자 매뉴얼.

<리스크와 대응>
가장 먼저 확인할 것은 라벨입니다. 보유 데이터에 정답 라벨이 없으면 라벨링 공수가 전체의 20%를 넘고, 그만큼 모델 개발이 줄어듭니다. 착수 2주 안에 라벨 보유 현황과 라벨링 필요량을 숫자로 확정해 알려드립니다.
두 번째는 촬영 조건입니다. 조도·각도·가림이 다양한 현장 이미지는 실내 데이터로 학습한 모델에서 정확도가 크게 떨어집니다. 조건별로 성능을 나눠 측정하고, 취약 조건은 촬영 가이드로 보완할지 모델로 더 학습할지 비용을 비교해 제안합니다.
세 번째는 알림 피로입니다. 이상 건이 하루 수십 건 나오면 담당자가 보지 않습니다. 초기 임계값을 보수적으로 잡고 파일럿에서 조정하며, 건별 처리 결과를 남겨 다음 임계값 조정 근거로 씁니다.
네 번째는 개인정보·영상 보관입니다. 사람이 찍히는 이미지는 보관 기간과 접근 권한을 먼저 정하고, 원본 보관 기간을 지나면 자동 파기되도록 설정합니다.

<기대 결과>
150일 뒤에는 이상 건이 대시보드 한 화면에 모이고, 각 건마다 원본·판정 근거·유사 사례·처리 이력이 붙습니다. 담당자는 "왜 이게 이상인지"를 설명할 수 있고, 임계값은 파일럿 데이터로 조정된 값입니다. 모델 재학습은 관리자 화면에서 절차대로 돌릴 수 있어, 이후 개선을 외부에 다시 의뢰하지 않아도 됩니다.

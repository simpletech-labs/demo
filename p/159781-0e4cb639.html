<프로젝트 진단>
공고에서 확인한 사실부터 적겠습니다. 화면·로그인·결제, 생성 흐름(자료 찾기 → 생성 → 사실 점검 → 고쳐 쓰기), 기출 데이터, 자동 검사 일부, hwpx 출력이 이미 운영 중이고 이번 범위가 아닙니다. 새로 만드는 것은 두 기능에 붙일 품질 고도화 로직의 템플릿입니다. 따라서 과제는 기능 추가가 아니라, 지금 특정 기능에 붙어 있는 고도화 절차를 데이터와 기준표로 구동되는 재사용 단위로 분리하는 일입니다.
이 구조에서 실패하는 방식은 세 가지로 정해져 있습니다. 첫째, 프롬프트 문자열을 템플릿이라 부르면 두 번째 기능에서 재사용되지 않습니다. 둘째, 채점을 LLM 단일 판정으로 두면 같은 답안에 점수가 흔들려 고쳐 쓰기가 수렴하지 않습니다. 셋째, 기준표를 코드에 하드코딩하면 기획자가 기준을 바꿀 때마다 배포가 필요합니다.
그래서 이번 MVP의 완료 판정을 기능 수가 아니라 재사용성으로 잡았습니다. 템플릿 1개를 코드 수정 없이 새 데이터와 새 기준표로 교체해 끝까지 돌릴 수 있는지를 기준으로 삼고, 그것을 골든셋 점수로 증명하는 구성입니다.

<작업 범위>
진행할 범위는 다섯 항목입니다.
1. 템플릿 정의 스키마 — 입력 데이터 스키마, 기준표, 프롬프트 조립 규칙, 채점 규칙, 재작성 정책의 5요소를 버전이 있는 하나의 단위로 정의합니다. 저장은 PostgreSQL(Supabase) JSONB와 버전 테이블을 씁니다.
2. 실행 파이프라인 — 분석 → 생성 → 채점 → 재작성(최대 2회) → 통과 판정. Python 워커로 두고 Node API에서 호출합니다. 타임아웃·토큰 초과·형식 오류의 재시도 규칙을 포함합니다.
3. 채점기 2단 — 규칙 기반 결정적 검사(문항 형식, 정답 유일성, 서식 필드 누락, 금칙어)를 먼저 돌리고, LLM 보조 판정(기준표 항목별 통과·부분·실패와 근거 문장)을 뒤에 붙입니다. 최종 점수는 규칙 결과를 우선 반영합니다.
4. 템플릿 2종 적용 — 시험 문제 생성, 행정업무 서식 작성. 기존 hwpx 출력과 자동 검사에 연결합니다.
5. 운영자 콘솔 — 템플릿 등록·버전·활성화, 기준표 편집, 골든셋 실행, 실행 로그와 점수 추이 조회. Next.js 화면 4개입니다.
제외할 범위는 화면·로그인·결제, 기존 생성 흐름 자체, 기출 데이터 수집, hwpx 렌더러, 파인튜닝입니다. 품질은 프롬프트·검색·채점으로 올리는 범위까지만 다룹니다.
추가로 제안하는 항목은 골든셋 30문항 기준의 회귀 리포트입니다. 템플릿 변경 전후 점수를 비교해 주는 장치로, 템플릿을 늘릴수록 필요해지므로 V2로 미루는 것보다 지금 2일을 넣는 편이 싸게 끝납니다.

<실행 플랜>
D1–D3 (11.24–11.26) 기존 저장소·프롬프트·자동 검사 코드 파악, 템플릿 스키마 확정, 골든셋 30문항 구성
D4–D6 (11.27–11.29) 실행 파이프라인 골격, 실패·재시도 처리
D7–D9 (11.30–12.02) 채점기 2단, 항목별 점수·근거 저장
D10–D12 (12.03–12.05) 템플릿 1호(시험 문제) 적용, hwpx 출력 연결, 1차 측정
D13–D15 (12.06–12.08) 템플릿 2호(행정 서식) 적용
D16–D17 (12.09–12.10) 운영자 콘솔 4화면
D18–D20 (12.11–12.13) 골든셋 재측정, 기준 미달 항목 튜닝, 인수인계 문서
총 공수 20일 / 지원 기간 30일 중 버퍼 10일. 남는 10일은 기존 코드 파악 지연과 템플릿 1호 튜닝에 배정했고, 중간 리뷰 3영업일을 포함합니다. 리뷰가 밀리면 전체 일정이 같은 일수만큼 뒤로 갑니다.

<리스크와 대응>
첫째, 기존 코드 접근입니다. 이 프로젝트에서 가장 먼저 확인할 항목이고, 늦어지면 첫 주가 통째로 멈춥니다. 착수 첫날 저장소 읽기 권한, 스테이징 DB, 개발용 LLM API 쿼터 세 가지를 받는 것을 계약 조건으로 둡니다.
둘째, 채점 기준의 주관성입니다. 기준표가 문장으로만 있으면 LLM 판정이 흔들립니다. 항목을 판정 가능한 형태로 쪼개고, 골든셋 30문항에서 사람 채점과 80% 이상 일치하는지를 완료 기준으로 삼습니다. 미달이면 기준표 문구를 고치는 것이지 모델을 바꾸는 것이 아닙니다.
셋째, 품질 목표 미달입니다. 20일 안에 목표 점수에 못 닿을 수 있습니다. 그때는 템플릿을 1종으로 줄이고 2호를 V2로 넘기되, 1호의 회귀 리포트는 완성해 넘깁니다. 판단 시점은 D15 리뷰로 미리 정해 둡니다.
넷째, hwpx 연동입니다. 기존 렌더러를 수정하지 않고 데이터만 넘기는 방식으로 붙입니다. 렌더러 자체를 고쳐야 하는 상황이 나오면 그 부분만 별도 견적으로 분리해 일정을 지킵니다.

<기대 결과>
완료 시점에 프롬프트를 고치려고 개발자를 부르지 않아도 됩니다. 기준표와 데이터를 콘솔에서 바꾸고 골든셋을 돌리면 점수 변화가 숫자로 남습니다. 세 번째 기능은 기존 템플릿을 복제해 기준표만 새로 쓰면 되고, 그 절차는 인수인계 문서에 3단계로 정리해 드립니다. 품질이 느낌이 아니라 점수 추이로 관리되는 상태가 되고, 회귀 리포트가 있으므로 다음 개선의 판단 근거도 함께 남습니다.

<확인이 필요한 질문>
1. 기존 서비스 저장소와 스테이징 환경 접근 권한을 주실 수 있습니까? 프레임워크 버전과 배포 방식도 알려주시면 첫 주 일정이 확정됩니다.
2. 골든셋으로 쓸 기출 데이터와, 현재 사람이 검수할 때 쓰는 체크리스트를 받을 수 있습니까? 채점 기준표의 출발점이 됩니다.
3. 사용 중인 LLM 공급자와 월 호출 한도는 어떻게 됩니까? 개발·측정용 쿼터를 별도로 주시는지 확인이 필요합니다.
4. 행정 서식 작성 기능의 산출물 범위(서식 종류 수, hwpx 템플릿 수)를 알려주십시오. 10종을 넘으면 템플릿 매핑 작업을 추가로 잡아야 합니다.
5. 템플릿을 앞으로 몇 종까지 늘릴 계획입니까? 5종 이상이면 콘솔에 복제·비교 기능을 넣는 편이 총비용이 낮습니다.

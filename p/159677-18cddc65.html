Q1. 스룩페이 연동 API를 받지 못하면
주문 수집은 스룩페이 판매자센터 주문 엑셀 업로드를 기본 경로로 두고, 업로드 즉시 채널 주문번호 기준으로 중복·누락을 검사해 통합 주문 장부에 반영합니다. 상품 등록은 몰 업로드용 엑셀을 시스템이 규격에 맞춰 자동 생성하고, 담당자가 업로드 후 결과 파일을 다시 넣으면 성공·실패 건이 주문과 함께 추적됩니다. 두 경로 모두 채널 어댑터로 분리해 두어, 나중에 API가 열리면 엑셀 업로드 대신 API 수집으로 교체만 하면 됩니다. 화면과 정산 로직은 바뀌지 않습니다.
Q2. 네이버 스마트스토어 커머스API 연동 경험
주문 수집·상품 등록을 채널별 어댑터로 분리하고, 인증 토큰 갱신과 수집 실패 재시도를 공통 계층에서 처리하는 구조로 작업한 경험이 있습니다. 커머스API의 경우 상품 등록은 카테고리·옵션·고시정보 매핑이 실제 난이도이고, 주문 수집은 상태 동기화(취소·반품·교환)와 중복 방지가 핵심입니다. 구체 사례와 화면은 플랫폼 메시지로 요청 주시면 정리해 보내드립니다.

<프로젝트 진단>
지금 비용은 사람이 아니라 반복에 있습니다. 채널별 주문을 각각 내려받아 엑셀로 합치고, 같은 상품을 몰마다 따로 등록하고, 거의 매일 셀러·브랜드별 정산액을 계산해 이체하는 구조입니다. 자동화의 대상은 이 세 가지 반복이고, 설계의 중심은 정산입니다. 매일 실제 돈이 나가므로 계산이 틀리면 바로 사고가 됩니다. 그래서 ①정산은 일 단위 마감으로 설계하고 ②금액이 맞지 않는 예외만 사람이 보게 하며 ③마감 후 수정은 이력과 사유를 남기는 구조가 되어야 합니다. IT 프로젝트가 처음이고 사내 개발자가 없다는 점도 설계 조건입니다. 화면에서 무슨 일이 일어났는지 확인할 수 있어야 하고, 요구사항은 문서로 남겨야 합니다.

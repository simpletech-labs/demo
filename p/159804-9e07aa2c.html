<프로젝트 진단>
바이브 코딩으로 만든 서비스가 상용화 단계에서 먼저 멈추는 곳은 화면이 아니라 운영 계층입니다. 무료 플랜 서버는 일정 시간 요청이 없으면 잠들고, 깨어나는 동안 첫 응답이 수십 초 걸립니다. 파일을 서버 로컬 디스크에 저장하면 재배포 한 번에 첨부가 사라집니다. 결제를 붙여도 결제 상태가 DB에 남지 않으면 유료 회원과 무료 회원을 코드가 구분하지 못합니다. 세 가지 모두 기능 추가가 아니라 구조를 바꾸는 일이라, 순서를 정해두지 않으면 매번 앞 단계를 다시 뜯게 됩니다. 그래서 ①실행 환경 분리 ②파일 저장 분리 ③결제 상태를 데이터로 남기기 순서로 진행할 것을 제안합니다. 직접 만드신 코드이므로 제가 먼저 읽고 구조를 문서로 정리한 뒤 손대는 방식으로 갑니다.

<작업 범위>
진행할 범위 — 현재 코드와 실행 환경 인수, 환경변수·시크릿 분리, 상용 서버 이전과 도메인·HTTPS 연결, 파일 업로드를 오브젝트 스토리지로 이전, PG 결제 연동(요청·승인·취소), 웹훅 수신과 중복 처리(같은 웹훅이 두 번 와도 한 번만 반영), 결제 상태와 이용 권한 매핑, 관리자 화면에서 결제 내역·환불 조회, 로그·백업·장애 복구 절차 문서 1장.
제외할 범위 — 법률 검토 결과의 품질(프롬프트·모델 선정) 개선, 약관과 개인정보 처리방침의 법률 검토, 신규 기능 기획, 마케팅 페이지 제작.
추가 제안 — 무료 체험 기간과 쿠폰 코드, 정기결제 실패 시 재시도와 안내 메일. 필요하시면 지금 함께 진행하거나 오픈 후에 붙일 수 있습니다.

<실행 플랜>
착수일 기준 30일, 4주 구성입니다.
1주 — 코드 인수와 구조 정리. 실행 재현, 화면·API 목록, 외부 연동 목록, 시크릿 하드코딩 점검. 게이트: 구조 문서 확인.
2주 — 서버 이전과 파일 저장 분리. 스테이징에 먼저 올리고 기존 파일 이전, 도메인 전환은 마지막에. 게이트: 스테이징에서 업로드·조회 확인.
3주 — 결제 연동. 테스트 키로 결제·취소·웹훅 전 구간, 중복 웹훅과 실패 응답 케이스까지. 게이트: 테스트 시나리오 결과표.
4주 — 운영 전환. 실키 전환, 모니터링과 백업, 인수인계 문서와 30분 화면 공유.
총 공수 28일 / 30일 중 버퍼 2일. 검토 피드백은 3영업일 안에 반영하고, 늦어지는 만큼 전체 일정이 같이 밀립니다.

<리스크와 대응>
가장 먼저 확인할 것은 저장소 접근과 실행 재현입니다. 코드를 받아도 환경이 재현되지 않으면 일정이 시작되지 않으므로 착수 3일 안에 판정하고, 막히면 범위를 다시 좁혀 견적을 냅니다. 둘째, PG 가맹점 심사입니다. 심사 전에는 테스트 키로만 검증되므로 착수와 동시에 신청을 진행해 주시고, 늦어지면 4주차 실키 전환만 뒤로 미루고 나머지는 그대로 갑니다. 셋째, 무료 서버에 쓰던 API 키가 코드에 남아 있으면 전부 새로 발급합니다. 넷째, 법률 문서에는 의뢰인 정보가 들어갑니다. 저장 항목과 보관 기간은 클라이언트가 정하고, 개발 쪽은 저장 위치·암호화·접근 권한까지만 책임집니다.

<기대 결과>
완료 시점에 서버가 재시작되거나 재배포돼도 첨부와 로그인이 유지되고, 결제가 들어오면 이용 권한이 사람 손 없이 반영됩니다. 코드는 직접 고칠 수 있는 상태로 남기되, 배포·백업·장애 대응 절차를 문서 한 장으로 갖게 됩니다. 결제 내역과 환불은 관리자 화면에서 확인합니다.

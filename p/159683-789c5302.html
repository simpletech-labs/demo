<프로젝트 진단>
공고에서 확인되는 조건은 세 가지입니다. 첫째, 11월 28일 개발 완료·12월 1일 납품으로 날짜가 고정되어 있고 예상 기간은 7일입니다. 둘째, 백엔드 서버 구축과 외부 유료 API 실연동은 범위에서 빠져 있습니다. 셋째, AI 제작 도구로 만든 시제품과 상세 기획서가 이미 있습니다. 그래서 이 프로젝트의 난이도는 기능 구현이 아니라 "시제품을 그대로 내지 않고, 시연에서 끊기지 않는 화면으로 다시 세우는 일"에 있습니다. 지원자가 178명인 공고이므로 판단 기준은 금액보다 "7일 안에 끝난다는 확신"이라고 봅니다.

<작업 범위>
진행할 범위 — 사택 관리의 다섯 흐름(발령 등록, 계약, 입주, 월별 비용, 반납)을 화면으로 완성합니다. 상세 기획서의 화면 목록을 기준으로 목록·상세·등록 폼·상태 변경, 대시보드 요약, 검색·필터, 더미 데이터 기반 페이징을 구현합니다. 데이터는 브라우저 저장소와 목업 JSON으로 처리해 새로고침 후에도 시연 흐름이 유지되게 합니다. 시제품의 화면 구조와 문구는 유지하되, 여백·정렬·표·폼 상태처럼 시연에서 눈에 걸리는 부분을 정리합니다.
제외할 범위 — 실제 DB·인증 서버·배포 인프라, 외부 유료 API 연동, 권한별 계정 관리, 모바일 앱, 기획서에 없는 신규 기능.
추가 제안 — 시연 리허설 1회(30분 화상, 시나리오 3개를 순서대로 클릭하며 끊기는 지점 점검)를 무상으로 포함합니다. 실제 서버·DB가 필요한 2단계는 별도 견적으로 분리합니다(추정 1,000,000원/5일, 요구사항 확정 후 재산정).

<실행 플랜>
11.20 착수 기준 7일, 총 공수 7 M/D(1인). 버퍼는 납품 전 점검에 씁니다.
D1(11.20) 기획서·시제품 코드 인수, 화면 목록 확정, 스택과 폴더 구조 결정. 산출물: 화면 목록표.
D2(11.21) 공통 레이아웃·내비게이션·디자인 토큰(색·간격·타이포) 정리.
D3~D4(11.22~11.23) 발령·계약·입주 화면, 목록·상세·폼·상태 변경.
D5(11.24) 월별 비용·반납 화면, 대시보드 요약.
D6(11.25) 더미 데이터 연결, 검색·필터, 화면 간 이동 점검.
D7(11.26) 시나리오 3개 리허설, 결함 수정, 소스·실행 안내 전달.
11.27~11.28 버퍼 — 발주사 확인 후 수정 반영. 12.1 납품.

<리스크와 대응>
가장 큰 불확실성은 기획서와 시제품 코드의 상태입니다. 시제품이 "화면은 있으나 흐름이 끊긴" 상태라면 7일 중 사흘이 재작업에 들어갑니다. 그래서 D1에 인수 확인을 먼저 하고, 화면 목록을 한 번에 확정한 뒤 착수합니다. 확정 이후 추가 화면은 1화면당 0.5일씩 일정에 반영해 먼저 알려드립니다. 두 번째는 시연 환경입니다. 발표장 네트워크를 믿을 수 없으므로 로컬 실행본과 정적 빌드 두 가지로 전달하고, 노트북에서 바로 열리는지 D7에 확인합니다. 세 번째는 개발 완료일과 납품일 사이의 이틀입니다. 이 기간은 수정 요청만 받고 신규 기능은 받지 않는 것을 전제로 견적을 잡았습니다.

<기대 결과>
완료 시점에 남는 것은 "기획서를 설명하지 않아도 되는 시연"입니다. 발령 등록에서 반납까지 다섯 단계를 끊김 없이 클릭으로 보여줄 수 있고, 같은 시연을 담당자가 혼자 반복할 수 있습니다. 화면이 시제품보다 정돈되어 있어, 플랫폼의 완성도가 아니라 진행 의지로 읽히지 않게 됩니다. 소스와 실행 안내가 남으므로 이후 실제 서버를 붙이는 2단계는 화면을 그대로 두고 데이터 계층만 교체하는 방식으로 이어갈 수 있습니다.

1. 시제품 코드와 상세 기획서를 11.20 착수 전에 받을 수 있을까요? 리포지토리인지 압축 파일인지도 알려주세요.
2. 시연에서 반드시 보여야 하는 시나리오 3개를 정해 주실 수 있나요? 나머지는 목록 수준으로 두고 7일을 그쪽에 집중하는 편이 안전합니다.

4. 기획서에 정의된 화면 수를 알려주시면 7일 안에 가능한 범위를 그 자리에서 확정해 드리겠습니다.

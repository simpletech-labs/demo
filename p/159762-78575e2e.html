<프로젝트 진단>
이 프로젝트에서 무너지는 지점은 기능 부족이 아니라 금액과 상태가 어긋나는 순간입니다. 금액변동형 MPM은 예비필드 10바이트 자리에 결제금액이 들어가고, QR구분 1·등록기관ID 2·가맹점ID 12·단말기ID 16·예비필드 10·체크문자 4바이트가 고정 길이로 붙습니다. 한 바이트만 밀려도 금액이 다른 가맹점으로 가거나 0원 승인이 나고, 그 보정은 정산 단계 수작업으로 돌아옵니다. 그래서 파싱을 범용 라이브러리에 맡기지 않고 필드 오프셋·길이·문자집합·체크문자 대조를 명시적으로 구현하고, 검증 실패는 금융결제원 전문 송신 전에 끊는 것을 첫 원칙으로 잡습니다. 기존 고정형 40바이트와 신형 50바이트는 길이 판별 후 분기하되 검증 규칙은 한 벌로 유지합니다.
두 번째는 상태입니다. 결제·승인취소·망취소는 응답 유실 구간에서 원장이 갈라집니다. 거래고유번호 기준 상태 머신과 멱등 저장을 코어에 두고, 타임아웃은 실패가 아니라 미확정으로 다뤄 망취소와 대사로 수렴시킵니다. 세 번째는 대사입니다. 내 원장·금융결제원·가맹점 원장 세 곳을 처음부터 맞추는 구조를 넣지 않으면 운영 인력이 매일 수기로 메우게 됩니다. 업무에서 결제·취소·환불 처리와 월별 정산 배치를 맡으며 이 세 지점이 실제로 터지는 곳임을 겪었습니다.

<작업 범위>
진행할 범위 1) 요구사항 분석, 전문 규격서·아키텍처·DB·API 설계 2) 금액변동형 QR 파싱·무결성 검증 모듈(40/50바이트 공존) 3) 결제·승인취소·망취소·입금·정산 통합 중계 코어와 거래 상태 머신 4) 금융결제원 전용회선·VPN 경유 전문 송수신 모듈(재접속·재전송·원문 로그) 5) 가맹점·제휴사 표준 RESTful API와 전문 인터페이스(멱등키·서명 검증) 6) 관리자 관제 웹(가맹점·단말기, 실시간 거래, 대사, 장애·로그) 7) 단위·통합·피크타임 부하 테스트와 결과서 8) 웹 취약점·소스코드 보안약점 진단 조치 9) 시범 매장 파일럿 검증 지원과 인수인계 문서.
제외 범위: 가맹점 단말 앱, POS·KIOSK 제조사별 커스텀 개발(표준 API 제공까지), 금융결제원 이용기관 심사 대행, 외부 진단기관 용역비(진단 결과 조치 개발은 포함).
스택 선택 이유입니다. 백엔드는 권장안대로 Java 1.8+/Spring Boot를 씁니다. 선언적 트랜잭션, Spring Scheduler 기반 정산 배치, 고정 길이 전문 처리를 한 프레임워크에서 정리할 수 있고 세 가지 모두 업무에서 운영해 본 조합입니다. DB는 Oracle 또는 MariaDB 중 클라이언트 표준을 따르며, Redis는 주문 단위 분산 락과 거래 상태 캐시에 씁니다. 락은 Redis로 1차 차단하고 거래고유번호 유니크 제약으로 DB에서 다시 막는 이중 구조입니다. Scale-out은 무상태 API + Redis 세션 + Docker 이미지 롤링 배포로 구성해 배포 중 거래가 끊기지 않게 합니다.

<리스크와 대응>
첫째, 전용회선·VPN·이용기관 코드입니다. 개발이 끝나도 실회선 검증이 막히면 일정이 그대로 밀립니다. 착수 즉시 신청 주체와 일정을 확인하고, 개통 전까지는 규격 기반 모의 응답기로 선행 개발한 뒤 실회선에서 규격 대조표로 재검증합니다. 둘째, 목표 TPS와 응답시간이 숫자로 확정되지 않았습니다. 측정 전 수치는 약속하지 않고, 시나리오와 합격 기준을 문서로 합의한 뒤 수행해 실측값 그대로 제출합니다. 셋째, 망취소 정책입니다. 응답 유실 시 자동 망취소인지 수동 확인인지에 따라 코어 흐름이 달라지므로 설계 초기에 확정합니다. 넷째, 연동처별 전문 차이는 어댑터 계층으로 분리해 코어가 흔들리지 않게 합니다.

3) 파일럿 기간 결제·취소·입금·정산 3자 대사 금액 일치, 미결 건은 사유 코드로 전량 설명 가능
4) 합의한 피크 TPS에서 오류율과 p95 응답시간 기준 충족, 실측 결과서 제출
네 가지 모두 문서와 측정값으로 남기므로 인수 후에도 같은 기준으로 검증할 수 있습니다.

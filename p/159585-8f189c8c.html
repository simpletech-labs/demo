Q1 적합한 기술 스택과 선택 이유(비개발자 기준)
고객·협력업체는 모바일 웹(PWA), 관리자는 반응형 웹으로 만들고 세 화면이 하나의 API와 권한 체계를 공유하도록 Next.js + Node.js(NestJS) + PostgreSQL을 제안합니다. ①PWA는 앱 설치 없이 카메라·사진 업로드가 되어 비회원 고객이 문자 인증 후 바로 접수할 수 있습니다. ②세 화면이 같은 API를 쓰므로 견적·수금 상태가 한 곳에서만 바뀝니다. ③PostgreSQL은 금액·상태 변경을 트랜잭션으로 묶어 수금 기록에 적합합니다.

Q2 이 프로젝트의 성공 기준에 대한 전문가 의견
성공 기준은 기능 목록이 아니라 운영 지표로 두는 것이 맞습니다. ①비회원 고객이 문자 인증→사진 접수→견적 선택까지 5분 안에 완주한다. ②추가 작업은 관리자·고객 승인이 모두 기록되기 전에는 완료로 넘어가지 않는다(예외 0건). ③수금은 두 기록이 남고 금액·일시·방법이 다르면 자동 불일치 표시된다. ④관리자 1명이 시범 20곳·월 200건을 추가 인력 없이 처리한다. ⑤2차 정산·자동화를 붙일 때 1차 테이블을 다시 만들지 않는다.

Q3 미정 범위 9개 항목의 포함 여부와 확장 방법
부록 A에 9개 항목을 포함·제외와 별도 견적으로 나눴고, 기본 범위에는 넣지 않는 것을 권합니다. 대신 확장 지점(테이블·상태 필드·API 훅)만 1차에 미리 뚫어 두어 2차에서 화면과 데이터 구조를 다시 만들지 않게 합니다.

Q4 2차 확장 대비 설계와 이중 승인·수금 불일치 상태 정리
상태는 문자열 컬럼이 아니라 상태 정의 테이블(코드, 진입 조건, 다음 상태, 담당 역할)로 두고 모든 전이를 이력에 남깁니다. 금액은 원장 테이블에 +/− 행으로만 쌓아 잔액을 계산하므로 부분 수금·환불·조정을 2차에 붙여도 1차 데이터를 고치지 않습니다. 추가 작업은 approval 테이블에 요청자·승인자·역할·시각·금액을 행으로 남기고 두 승인 행이 모두 있어야 완료 전이를 허용합니다. 수금 불일치는 예상·수령 금액 차이를 mismatch로 표시하고 해소 시 사유 코드를 남깁니다.

Q5 업무 흐름·승인·금액 정합성 구축 경험과 실제 투입 인력
신청→승인→처리→정산 흐름이 있는 운영 플랫폼과 금액·상태 정합성이 중요한 정산 화면 구축 사례를 담당 범위와 함께 정리했습니다. 실제 투입은 풀스택 2명이 직접 수행하고 하도급은 쓰지 않으며 대표가 PM을 겸합니다.

Q1. 거래처마다 다른 요율·인센티브·최소 정산 기준·프로모션이 겹칠 때 적용 순서와 검증 방식
정산 계산은 코드에 조건문을 쌓지 않고 정책을 데이터로 등록하는 구조로 만듭니다. 요율표, 인센티브, 최소 정산, 프로모션, 특별 정산을 각각 기간을 가진 정책 레코드로 두고, 적용 순서를 명시적 우선순위 필드로 관리합니다. 계산은 ①기간 유효 정책 조회 ②우선순위 정렬 ③순차 적용 ④적용 근거를 계산 로그로 남김 순서로 돌립니다. 검증은 두 겹입니다. 첫째, 과거 엑셀 정산 결과를 기대값으로 넣고 같은 입력에 같은 금액이 나오는지 자동 대조합니다. 둘째, 계산 결과마다 어떤 정책이 어떤 순서로 적용됐는지 화면에서 펼쳐 볼 수 있게 해, 실무자가 숫자 대신 근거를 확인하고 이의를 판단하게 합니다. 정책이 70곳으로 늘어도 코드 배포 없이 정책 등록만으로 반영됩니다.
Q2. 각도·양식이 일정하지 않은 화면에서 OCR로 숫자를 읽은 경험
촬영 각도와 양식이 매번 다른 이미지는 인식률 자체보다 인식 결과를 확정하지 않는 설계가 중요합니다. 제가 다룬 방식은 ①전처리(원근 보정·기울기 정정·대비 정규화) ②표 구조 검출 후 셀 단위 인식 ③필드별 신뢰도 점수 부여 ④임계값 미만은 빨간 표시로 사용자 확인 ⑤확정 전에는 실적에 반영하지 않음, 이 다섯 단계입니다. 틀린 값을 걸러내는 장치는 세 가지입니다. 숫자 필드는 허용 범위(약가·수량 상한)를 벗어나면 자동 반려, 같은 처방의 합계와 개별 항목 합이 다르면 반려, 재촬영이 필요한 사진은 사유와 함께 즉시 재요청입니다.

<프로젝트 진단>
이 프로젝트의 난이도는 화면 수가 아니라 두 곳에 있습니다. 첫째, 제약사 70~80곳의 요율표 양식이 모두 다르고 인센티브·최소 정산·프로모션이 중첩됩니다. 엑셀을 그대로 옮기면 같은 문제가 반복되므로, 정책을 데이터로 표현하는 정산 엔진이 먼저입니다. 둘째, OCR입니다. 몇 년 전 인식률 60~70%로 접었다는 이력이 있으니 인식률 숫자를 약속하는 제안은 신뢰를 얻기 어렵습니다. 답은 인식률이 아니라 확정 전 사람 확인과 재촬영 유도, 그리고 확인에 드는 시간을 줄이는 화면입니다.

<작업 범위>
진행할 범위 — 기획(요구사항·화면 설계·정산 규칙 정의서), 관리자 웹 40화면, 딜러 앱 iOS·Android, API 서버·DB, OCR 연동, 클라우드 구축·배포·백업·모니터링, 스토어 배포, 기준정보·요율표·실적 이관, 운영 매뉴얼·이관 절차서·교육.
기술 스택 — 웹은 Next.js·TypeScript, 서버는 NestJS, DB는 PostgreSQL, 큐는 Redis+BullMQ(정산 배치·OCR 작업), 앱은 React Native(Expo)로 iOS·Android를 한 코드로 만듭니다. 인프라는 AWS 서울 리전, OCR은 클라우드 OCR에 표 구조 후처리 파서를 붙입니다. 한 언어(TypeScript)로 웹·서버·앱을 덮으면 인력이 한 명 빠져도 유지보수가 됩니다. 세금계산서 홈택스 연동은 이번 범위에서 제외하고 발행 내역 관리까지만 구현합니다.
제외할 범위 — 홈택스 직접 발행, 매입처 자동 발주 전송, 회계 프로그램 연동, 실제 결제·송금 실행, 모바일 웹 버전, 다국어.
추가 제안(별도 견적, 기본가에 미포함) — ①과거 실적·정산 3년치 이관 6,000,000원 ②요율표 원본 파일 자동 변환 9,000,000원 ③수취 정산서 원본 양식 인식 7,000,000원 ④홈택스 전자세금계산서 발행 5,000,000원. 각 항목은 나중에도 붙일 수 있습니다. 이관은 테이블 자리를 비워 두고 확정 소스만 연결하면 되고, 요율표·정산서 인식은 파서 모듈만 추가하는 구조이며, 홈택스는 발행 어댑터를 분리해 두어 인증키만 넣으면 됩니다.

<리스크와 대응>
첫째, 요율표 원본 확보입니다. 70~80곳 원본이 착수 후에나 모이면 정책 등록이 병목이 됩니다. 착수 1주 안에 3곳을 표본으로 받아 변환 규칙을 먼저 확정하고, 나머지는 실무자가 화면에서 입력하는 경로를 기본으로 둡니다. 둘째, 정산 금액 정합성입니다. 수취 정산서와 지급 정산서의 차액이 맞지 않으면 돈이 틀어지므로, 월 마감 전에 차액 사유 코드(요율 차이·최소 정산 미달·프로모션 누락·수기 조정)를 강제로 지정하게 하고 미지정 건은 마감을 잠급니다. 셋째, OCR 정확도입니다. 오픈 전 2주를 실제 처방 화면 표본 200건으로 측정하는 기간으로 잡고, 정확도 수치는 그 측정 결과로 보고합니다. 지금 숫자를 약속하지 않습니다. 넷째, 앱 스토어 심사와 위치·개인정보 정책입니다. 계정은 발주사 명의로 만들고 심사 리젝 사유 대응 절차를 매뉴얼에 넣습니다.

<기대 결과>
완료 시점에 ①요율표 엑셀 대조와 정산서 작성이 사람 손에서 사라지고 실무자는 차액 사유가 붙은 예외 건만 봅니다. ②딜러는 앱으로 처방 화면을 찍어 올리고 인식 결과를 확인·수정하는 것까지 앱에서 끝냅니다. ③정산 결과마다 적용 정책과 근거가 남아, 제약사·딜러 이의에 숫자가 아니라 근거로 답합니다. ④운영 매뉴얼·백업 복구 절차·운영사 이관 절차가 문서로 남아 다른 운영사로 넘길 수 있는 상태가 됩니다.

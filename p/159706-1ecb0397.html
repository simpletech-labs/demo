<프로젝트 진단>
이 공고의 성패는 "계산이 맞는가"가 아니라 "현장이 그 결과를 받아들이는가"에서 갈립니다. 플릿튠·루티를 검토하고도 쓰지 못한 이유가 김포 경유 코스라면, 원인은 계산 성능이 아니라 권역 조건이 계산식 안에서 지켜지지 않았기 때문입니다. 적재율을 조금 더 높이는 대신 권역을 넘는 답이 선택된 것이고, 같은 구조로 만들면 저희도 같은 결과를 냅니다. 그래서 권역은 절대 조건으로 고정하고, 그 안에서만 적재금액 한도와 거리를 줄이는 순서로 설계합니다. 결과가 조건을 어기면 점수가 아니라 탈락으로 처리합니다.
두 번째 판단은 발주와 배차를 한 덩어리로 만들지 않는 것입니다. 데이터는 같지만 계산 주기와 검증 방법이 다릅니다. 발주는 매일 아침, 배차는 배송일 전날입니다. 모듈을 나누면 발주를 먼저 검증해 쓰기 시작하고 배차는 뒤에 붙일 수 있어, 60일 안에 둘 다 끝내야 하는 부담이 줄어듭니다.
세 번째는 규칙을 문서로 먼저 고정하는 일입니다. 규칙 문서가 없다고 하셨으니, 담당자 설명을 규칙표로 바꿔 승인받은 뒤 개발을 시작합니다. 이 표가 없으면 검증 단계에서 "그게 아니"가 반복되고, 그때 무너지는 것은 일정이 아니라 결과에 대한 신뢰입니다.

<작업 범위>
진행할 범위
1) 규칙 정의서: 발주(현재고·출고·안전재고·발주 가능 요일·최소 발주 수량·유통기한)와 배차(권역·적재금액 한도·배송 요일·출발 거점 인천)를 표로 정리하고 승인받습니다. 산출물: 규칙표 v1.
2) 발주고 ERP 연동: 재고·출고·주문·매입처·품목을 읽기 전용으로 수집합니다. 일 1회 자동 + 수동 재수집, 실패 시 재시도와 수집 로그 화면. 발주 전송은 만들지 않습니다(공고대로).
3) 발주 수량 산출: 매입처 50곳·품목 600개 기준정보 화면, 안전재고 산출(최근 8주 출고 + 유통기한 보정), 매입처별·품목별 산출 목록과 엑셀 내려받기, 담당자 수동 조정과 사유 기록.
4) 배차 코스 산출: 권역 고정 + 차량별 적재금액 한도 + 배송 요일, 일 80건·18대 규모. 코스 조회·수동 조정(코스 간 이동), 코스표 인쇄.
5) 실데이터 검증: 과거 4주 데이터로 재현 테스트를 돌려 사람이 짠 코스와 비교표(차량 수, 총 주행거리, 권역 위반 0건, 적재 초과 0건)를 제출합니다.
제외할 범위: 매입처 시스템 자동 발주 전송, 당일 긴급 건 실시간 재배차, 운전자용 앱, 창고 재고 실사.
추가 제안: 차종별 적재 계수 반영 +3일/+1,200,000원, 2주 현장 파일럿 동행 +10일/+3,000,000원.

기술 선택(비개발자용 설명)
브라우저에서 여는 사내 웹 프로그램으로 만듭니다. 설치가 없어 담당자 PC를 가리지 않고, 화면은 Next.js, 서버는 NestJS, DB는 PostgreSQL을 씁니다. 코스 계산은 구글의 최적화 라이브러리(OR-Tools)로 "권역을 벗어나면 답에서 제외"라는 규칙을 계산에 직접 넣습니다. 엑셀로 하던 계산을 서버가 대신하고, 화면은 그 결과를 보여주고 고치는 역할만 합니다. 사내 서버나 AWS 어느 쪽이든 Docker로 옮길 수 있게 만들어, 나중에 이전할 때 다시 만들지 않아도 되게 합니다.

<리스크와 대응>
1) ERP API 정의서가 아직 없다면 착수 1주 안에 확정을 조건으로 잡습니다. 늦어지면 수집부를 목업으로 만들고 나머지를 먼저 진행합니다.
2) 규칙이 구두 설명에만 있으므로, 규칙표 승인 전에는 해당 모듈 개발을 시작하지 않습니다. 변경은 규칙표 개정으로만 받습니다.
3) 검증에서 현장 판단과 어긋날 경우를 대비해 D51~D56을 비교 검증에 고정 배정했습니다. 여기서 나온 불일치는 규칙 보정으로 처리하고, 알고리즘을 새로 만들지 않습니다.
4) 출고 이력이 8주보다 짧으면 안전재고 계수를 수동 입력으로 대체하고 그 사실을 화면에 표시합니다.

<기대 결과>
완료 시점에 남는 것은 프로그램 두 개가 아니라 "판단 기준을 적어 둔 규칙표 + 그 규칙대로 계산하는 도구"입니다. 발주 담당자는 목록대로 각 매입처 시스템에 입력만 하면 되고, 배차 담당자는 권역을 벗어난 코스를 걱정하지 않고 차종 차이만 손보면 됩니다. 규칙표가 있으므로 담당자가 바뀌어도 기준이 유지되고, 나중에 규칙을 바꿀 때도 어디를 고쳐야 하는지가 문서로 남습니다.

<확인이 필요한 질문>
1. 4주치 과거 데이터(주문·출고·차량 배정 결과)를 검증용으로 받을 수 있을까요? 사람이 짠 코스 이력이 있어야 비교표를 만들 수 있습니다.
2. 권역은 행정구역(동·읍면) 기준인지, 담당자가 쓰는 권역표가 따로 있는지 알려주세요.
3. 차종별 적재량은 지금 어떤 기준으로 조정하고 계신가요? 계수표가 있으면 3일 추가로 반영 가능하고, 없으면 1차에서는 수동 조정으로 두는 편이 안전합니다.
4. 미팅은 오프라인(인천 서구)이라고 하셨는데, 규칙 인터뷰는 담당자 두 분(발주·배차)과 각각 필요합니다. 시간을 얼마나 낼 수 있는지 알려주세요.
5. 서버는 사내 장비와 클라우드 중 어느 쪽을 선호하시나요? 사내 장비면 외부 접속 정책을 함께 정해야 합니다.
6. 발주고 ERP API 이용 요금과 호출 한도(일 호출 수 제한)를 알고 싶습니다. 한도가 낮으면 수집 주기를 조정해야 합니다.

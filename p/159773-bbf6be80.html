사전 검증 질문 답변
"자체 개발한 실시간 채팅 상담 솔루션을 보유하고 계신가요? 타사 솔루션을 연동·재판매하는 방식인지와 데모 확인 방법도 알려 주세요."
없습니다. 재판매도 하지 않습니다. 공고가 솔루션 보유 업체를 우선 검토한다고 명시했고, 저희는 그 조건에 해당하지 않습니다. 드릴 수 있는 것은 완성된 제품이 아니라 요구사항을 구현하는 구축입니다. 계약 전 확인 가능한 것으로 2주 동작 데모(위젯 삽입 → 비회원 상담 시작 → 자동 배정 → 이력 저장·재조회)를 만들어 화상으로 시연하고, 그 코드를 납품 범위에 그대로 넣는 조건을 제안합니다.
"기본 제공 기능과 별도 커스터마이징이 필요한 기능을 구분해 달라"는 질문에는 보유 제품이 없으므로 '기본 제공' 구분 자체가 성립하지 않습니다. 대신 전 항목을 A 표준 채팅(메시지·첨부·이력), B 상담 운영(자동 배정·재배정·자동 종료), C 연동(회원·주문 조회, 유입 경로) 세 묶음으로 나눠 항목별 공수와 금액을 분리해 드리겠습니다. 어느 묶음을 빼도 나머지가 동작하게 만듭니다.
"기존 PHP 쇼핑몰·관리자와 연동해 상담 내용을 자사 DB에 저장한 구축 사례가 있나요?" 없습니다. 외주 수행 실적이 없습니다. 업무에서 한 것은 JSP·Spring 기반 관리자 시스템과 MSSQL ERP의 일 단위 데이터 연동, 올더게이트·PayAt 결제모듈 연동, Redis·Celery로 동시 요청을 큐잉한 응찰 처리입니다.

<프로젝트 진단>
공고의 기능 15개를 세어 보면 채팅 자체(실시간 1:1, 파일 첨부, 이력 저장)는 3개이고 나머지 12개는 상담을 운영하는 기능입니다. 난점은 채팅창이 아니라 배정·이관·종료·연계입니다. 실제로 시간을 쓰는 지점은 셋입니다. 첫째, 로그인 없는 고객을 재문의 때 같은 사람으로 알아보는 방법. 둘째, 고객이 누르고 온 경로를 워크플로우로 남기는 일. 셋째, 상담 내용을 외부 클라우드가 아닌 자사 DB에 두면서 조회 성능을 유지하는 일. 채널톡·Chatwoot은 둘 다 대화가 외부에 저장되는 구조라 '자사 DB 저장' 조건과 맞지 않습니다. 이 조건 때문에 기성품보다 직접 구축이 총비용에서 유리한 지점이 생깁니다.

<작업 범위>
진행할 범위 1) 쇼핑몰 삽입형 위젯(비회원 즉시 상담, 반응형·WebView 대응) 2) 실시간 1:1 채팅(WebSocket, Redis Pub/Sub로 다중 서버 확장, 재접속 시 대화 복원) 3) 비회원 세션 식별과 재문의 이력 연계 4) 상담원 자동 배정·담당자 재배정·그룹별 관리 5) 상담원 콘솔(대기열, 다중 상담, 이력 검색, 상담 메모) 6) 유입 경로 수집과 워크플로우 표시 7) 채팅 내 입력폼 전송(상담 시작 전 고객 정보 폼 포함) 8) 이미지·파일 첨부(시안·견적서) 9) 기존 PHP 사이트 연동(삽입 스크립트 1개, 회원·주문 조회 API) 10) 상담 상태 관리와 Celery 기반 자동 종료 배치 11) 상담원별 현황 통계(응답 시간·건수) 12) 소스 이관과 운영 매뉴얼·교육.
제외 범위: 쇼핑몰 자체 리뉴얼과 디자인 개편, 카카오톡·외부 메신저 연동, AI 자동 응답, 결제·주문 처리 로직 변경, 상담원용 네이티브 앱. PHP 파일 수정은 삽입과 회원 식별 두 지점으로 한정하고, 나머지는 고객사 개발자 2명과 분담합니다.

<실행 플랜>
D1–D12 설계. 현재 PHP 쇼핑몰·관리자 구조, 회원·주문 테이블 접근 방식, 상담 유입 시간대 확인. 게이트 1: 상담 흐름 정의서·연동 방식·테이블 소유권 승인.
D13–D40 채팅 코어. 메시지 저장 스키마, 실시간 연결, 첨부, 재접속 복원.
D41–D60 상담 운영. 자동 배정 규칙, 재배정, 그룹, 대기열, 자동 종료 배치. 게이트 2: 상담원 콘솔 시연과 배정 규칙 확정.
D61–D75 연동. 위젯 삽입, 회원·주문 조회, 유입 경로, 입력폼.
D76–D85 통계·알림·권한, 동시 접속 부하 측정과 결과 보고서.
D86–D90 인수 테스트와 이관, 운영 교육·매뉴얼. 게이트 3(최종): 고객사 개발자 2명이 직접 설정을 바꿔 동작하는 것 확인.
게이트 승인 지연은 일정에 그대로 반영하며, 검토 의견은 3영업일 내 반영을 기준으로 합니다.

<리스크와 대응>
연동 리스크가 가장 큽니다. PHP 관리자 구조와 회원 식별 기준이 확인되기 전에는 위젯이 붙일 정보가 정해지지 않으므로 D1–D12에 확정하고, API를 열 수 없으면 서명된 식별값만 위젯에서 받는 방식으로 대체합니다. 비회원 식별은 쿠키·세션 조합으로 처리하되 연락처를 필수로 받지 않고, 보관 기간과 열람 권한을 D1에 정해 파기 배치를 넣습니다. 실시간 안정성은 메시지를 DB에 먼저 저장한 뒤 전송하는 순서로 만들어 연결이 끊겨도 대화가 남게 합니다. 자사 DB 저장은 백업·보관 주기를 함께 설계해야 하므로 인프라 범위를 D1에 합의합니다.

<기대 결과>
1) 상담원이 대화를 열 때 고객의 유입 경로·회원·주문 정보가 함께 보여 되묻는 왕복이 줄어든다. 2) 로그인 없이 시작한 상담이 재문의 시 이전 이력과 담당자로 이어진다. 3) 상담원 부재 시간 문의가 유실되지 않고 배정 대기로 남는다. 4) 상담 건수·응답 시간·종료 사유가 자사 DB에서 조회된다.

<확인이 필요한 질문>
1. PHP 쇼핑몰·관리자는 자체 개발인가요? 회원·주문 테이블 읽기 접근과 별도 API 유무를 확인하고 싶습니다.
2. 상담원은 몇 명이며 피크 동시 상담은 몇 건인가요? 배정 규칙(라운드로빈·부하 기준)을 정하는 근거가 됩니다.
3. '자사 DB'는 쇼핑몰과 같은 서버·같은 DB를 뜻하나요, 별도 DB 허용인가요?
4. 유입 경로는 어느 수준까지 필요하신가요? 페이지 단위인지 상품·주문 단계까지인지에 따라 수집 설계가 달라집니다.
5. 계약 전 2주 데모를 먼저 보시는 방식이 가능한가요? 솔루션 보유 조건을 충족하지 못하는 만큼 결과물을 먼저 확인하시는 편이 안전합니다.

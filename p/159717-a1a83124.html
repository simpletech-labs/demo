<프로젝트 진단>
문제는 대시보드가 아니라 적재 규칙입니다. 중복 적재가 한 번이라도 있으면 일매출이 부풀고 월 손익이 두 번 계산됩니다. 그래서 ①현재 구조·쿼리·스케줄 진단 ②적재 멱등성(같은 데이터가 두 번 들어와도 한 번만 반영) ③월 마감 스냅샷(마감 후 값이 바뀌지 않게) 세 가지를 먼저 고정합니다. BigQuery는 파티션과 클러스터링이 스캔량과 비용을 좌우하므로, 진단에서 쿼리별 스캔량을 뽑아 비용 기준으로 재설계합니다. 저는 GCP Cloud Composer에서 수집·검증 DAG를 개발했고, SQL 실행 분석으로 중복 조회를 찾아 쿼리를 줄이는 작업을 운영에서 해왔습니다.

<작업 범위>
진행할 범위
1) 진단: 테이블·뷰·스케줄·권한 목록화, 쿼리별 스캔량·비용 리포트, 중복 발생 지점 식별.
2) 재설계: 원천/정제/마트 3계층, 일자 파티션과 채널·상품 클러스터링, MERGE 기반 멱등 적재와 적재 이력 테이블.
3) 집계: 일매출, 채널별 매출·수수료·원가·배송비 손익, 기준표(수수료율·원가·배송비) 관리 화면.
4) 월 마감: 마감 시점 스냅샷 테이블, 마감 후 재계산 금지 규칙, 마감 후 조정 이력 분리.
5) 대시보드: 일매출 추이, 월 손익(채널·상품), 기준표 편집. 도구는 기존 환경에 맞춰 Looker Studio 또는 자체 웹 중 선택합니다.
6) 문서: 구조도, 기준표 정의서, 운영 절차서, 인수인계 세션.
제외 범위: 채널 API 신규 개발, 광고 성과 수집, 회계 시스템 전표 생성.

<리스크와 대응>
1) 기존 수치와 맞지 않는다는 지적이 가장 흔합니다. 전월 3개월 대조표를 만들어 차이 원인을 중복·기준표·환불·취소로 분류해 보여드립니다.
2) 채널 API 제약으로 원천 데이터가 부족할 수 있습니다. 수집 방식은 그대로 두고 정제 계층에서 표준화합니다.
3) 마감 후 소급 변경 요구가 생깁니다. 스냅샷과 조정 테이블을 분리해 원본을 건드리지 않고 조정 이력만 남깁니다.
4) 비용이 늘 수 있습니다. 파티션 프루닝과 쿼리 승인 규칙으로 스캔량을 관리하고 월 비용 리포트를 제공합니다.

<기대 결과>
경영진은 채널별 손익을 같은 기준으로 보고, 마감된 월은 값이 흔들리지 않습니다. 성공 기준은 ①중복 적재 0건 ②전월 대조 차이의 원인 설명 가능 ③마감 후 재계산 차단 확인 ④문서만으로 동일 구조 재현 가능 — 네 가지입니다.

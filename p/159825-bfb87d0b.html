사전 검증 질문 답변
1. 후보 구성: 시제품이 HTML/CSS/JS이므로 화면을 살리는 가장 짧은 경로는 재작성이 아니라 서버 템플릿 이전입니다. Supabase는 PostgreSQL 기반, Vercel은 서버리스라 정산·입금기한 배치에 불리합니다. Django/DRF + MariaDB(AWS RDS) + Docker + 포트원을 제안합니다. 포트원은 국내 카드·카카오페이·네이버페이에 강하지만 해외카드·알리페이·위챗페이는 채널이 갈리므로 해외 전용 PG 1곳을 병행하고, 두 채널 모두 결제 결과를 서버에서 재조회합니다.
2. 시제품 이전: 화면 60여 개를 URL 목록으로 뽑아 1:1 대응표를 만들고 CSS는 그대로 쓰고 마크업만 템플릿화합니다. 완료 기준은 대응표 100%, 5개 언어·5개 통화 전환 시 레이아웃 깨짐 0건, 기능 명세 항목별 동작 체크리스트 확인입니다.
3. 금액·마감 검증: 화면이 보낸 금액을 신뢰하지 않고 서버가 상품·옵션·인원·짐·할인·할증을 재계산해 결제 요청액과 대조하고, 불일치하면 결제를 막습니다. 마감은 날짜·상품별 잔여 좌석을 트랜잭션 잠금으로 잡아 초과 판매를 차단합니다.
4. 관리자 권한: 역할(전체 관리/운영 담당)과 메뉴·액션 단위 권한을 분리하고, 2단계 인증과 변경 이력(누가·언제·무엇을)을 함께 남깁니다. 권한·승인 프로세스는 B2B SaaS Admin에서 설계·운영한 경험이 있습니다.
5. 라인페이는 이번 범위 제외를 권합니다. 결제수단 1종 추가는 3~5영업일, 별도 견적 대상입니다. 환율 자동 갱신은 일 1회 배치로 고시 환율을 적재하고 예약 시점 스냅샷을 고정하는 방식이면 충분하며 2~3영업일입니다.
6. 경험: PG 결제·취소·환불 연동, Spring Scheduler 정산 배치, 응찰 동시성 처리, 멀티테넌시 Admin, 차량 배정·일정·알림, 다국어 서비스를 직장 업무로 수행했습니다.

<프로젝트 진단>
이 프로젝트의 난이도는 화면이 아니라 돈과 시간이 얽히는 지점에 있습니다. 예약 사고는 세 곳에서 납니다. 같은 날짜·차량에 두 건이 들어가는 중복, 결제는 됐는데 예약이 안 잡히는 상태 불일치, 부분 환불 금액이 어긋나는 계산 오류입니다. 예약 시점 환율 고정과 입금 기한이 겹치면 "얼마를 언제까지"가 흔들리므로, 화면 이전보다 상태 모델과 서버 재계산을 먼저 확정합니다. 120일은 적정하지만 해외 PG 심사가 외부 일정이라, 국내 결제로 먼저 오픈하고 해외를 후속 배포하는 경로를 병행 준비합니다.

<작업 범위>
진행: ①시제품 60여 개 화면을 디자인 유지한 채 Django 템플릿으로 이전, 5개 언어·5개 통화 ②DB 스키마(상품·옵션·차량·예약·결제·정산·이력)와 회원·구글/카카오/LINE 로그인 ③예약 엔진(달력·시간, 픽업/샌딩/왕복, 인원·짐에 따른 차량 자동 변경, 정원·짐 한도 검증, 서버 재계산, 환율 스냅샷, 입금 기한) ④결제(국내 카드·카카오페이·네이버페이, 해외카드·알리페이·위챗페이, 부분 환불, 웹훅 재처리) ⑤전액 입금 시 자동 확정, 기한 경과 미입금 일괄 취소 배치 ⑥알림(이메일·알림톡·LINE, 고객 언어별 템플릿·발송 관리) ⑦Admin(대시보드, 예약·입금, 기사 수동 배정, 일정 달력, 월별·기사별 정산 CSV, 상품·설정, 변경 이력) ⑧HTTPS·자동 백업·장애 알림, 도메인 연결과 배포.
제외: 기획·디자인 신규 제작, 스마트폰 앱, 라인페이, 기사 자동 배정.

<리스크와 대응>
해외 PG 심사 지연이 최대 변수입니다. 첫 주에 신청하고, 미승인 시 국내 결제만으로 오픈 후 해외를 붙이는 2단계 배포를 전제로 일정을 짭니다. 둘째, 알림톡·LINE은 발신 프로필·채널 승인이 필요해 템플릿 문구를 초기에 확정하고 미승인 시 이메일로 대체합니다. 셋째, 통화별 반올림·표시 규칙이 어긋나면 CS가 폭증하므로 설계서에 규칙을 못 박습니다. 넷째, 기사 배정·정산은 예외가 많아 관리자 수동 조정과 이력 기록을 남겨, 나중에 규칙을 좁힐 수 있게 합니다.

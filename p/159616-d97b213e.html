<프로젝트 진단>
이 프로젝트의 진짜 난관은 차량정보 API가 아니라 "부품과 차량의 호환 관계"입니다. 차량정보 API는 차종·연식·배기량 같은 제원을 알려줄 뿐, "이 부품이 이 차에 맞는가"는 알려주지 않습니다. 그래서 매핑 테이블(부품 SKU × 적용 차종·연식 범위)을 따로 만들어야 하고, 이게 비어 있으면 필터는 화면만 예쁜 껍데기가 됩니다. 두 번째는 카페24의 구조적 제약입니다. 카페24는 서버 코드를 넣을 수 없어 스킨(HTML·CSS·JS)과 앱 영역에서만 동작합니다. 차량정보 API 키를 브라우저에 두면 키가 노출되고 호출 한도도 금방 소진되므로, 키를 숨기고 캐시·호출 제한·로그를 담당하는 중계 서버를 두는 구성이 필요합니다. 세 번째는 차량번호 조회의 개인정보 문제입니다. 번호를 저장하지 않고 조회 즉시 차종 코드로 변환하는 방식으로 설계해야 합니다.

<작업 범위>
포함
- 기획: 카테고리·필터 IA, 부품 속성 스키마(차종·연식·엔진·좌/우·순정/비순정), 검색 시나리오 8종 정의서.
- 디자인: 메인, 카테고리, 차량 선택, 검색 결과, 상품 상세, 장바구니·주문서 — PC·모바일 스킨 디자인.
- 개발(카페24): 스킨 커스텀(PC·모바일), 차량 선택 위저드(① 차량번호 입력 조회 ② 차종·연식·엔진 3단 선택), 호환 부품 필터, 상품 상세의 "적용 차량" 표시, 검색 결과 정렬·페이지.
- 개발(중계 서버): 차량정보 API 프록시, 응답 캐시(동일 차량 반복 조회 차단), 호출 한도 관리, 오류·지연 로그, 매핑 테이블 DB.
- 매핑 관리: 관리자 화면에서 SKU별 적용 차종 등록·수정·일괄 업로드(CSV), 미매핑 SKU 목록 리포트.
- 데이터: 부품-차량 매핑 1,000 SKU 초기 적재.
- 오픈: 결제·배송 정책은 카페24 기본 기능 사용, 주문 흐름 테스트 12건, 운영 매뉴얼 1부, 오픈 후 1개월 하자 수정.

제외
- 부품 사진 촬영·상세 카피, 맞춤형 풀 개발(카페24 밖 자체 프론트), 재고·ERP 연동, 견적 요청(RFQ) 기능, 매핑 1,000 SKU 초과분(별도 견적), 앱.

W4~8 중계 서버(프록시·캐시·로그), 필터 로직, 상품 상세 적용 차량 표시.
W6~9 매핑 1,000 SKU 적재, 관리자 매핑 화면, CSV 일괄 업로드.

<리스크와 대응>
1) 부품-차량 매핑 데이터 부재 — 가장 먼저 확인할 항목입니다. 매핑 원본(엑셀·카탈로그)이 있으면 1,000 SKU를 9주차까지 적재합니다. 없다면 차종·연식 범위를 사람이 판단해 넣어야 해 SKU당 공수가 발생하므로, 그 경우 적재량을 줄이거나 별도 견적으로 분리합니다. 필터를 "정확도 100%"로 약속하지 않는 이유입니다.
2) 차량정보 API 계약·요금·한도 — 발주사 명의로 계약해야 하고, 호출 한도가 낮으면 실사용에서 막힙니다. 캐시로 반복 호출을 줄이고, 한도 초과 시 안내 메시지를 띄우는 방식으로 방어합니다.
3) 카페24 제약 — 외부 서버 호출이 막히는 영역이 있어 스킨 내 스크립트로 중계 서버를 호출하는 구조로 갑니다. 카페24 앱 등록·심사가 필요한 기능은 사전에 확인해 일정에 반영합니다.
4) 차량번호 개인정보 — 번호 원문을 저장하지 않고 조회 직후 차종 코드로 변환, 로그에는 마스킹만 남깁니다. 보관 정책을 1주차에 문서로 확정합니다.
5) 오주문 클레임 — 부품 상세에 "적용 차종"을 명시하고, 장바구니 단계에서 선택 차량과 호환 여부를 한 번 더 검사해 경고합니다.

<기대 결과>
90일째에 ①고객이 차량번호 또는 차종·연식을 고르면 그 차에 맞는 부품만 남고 ②상품 상세에 적용 차종이 보이며 ③담당자가 CSV로 매핑을 직접 갱신하고 미매핑 SKU를 확인할 수 있고 ④차량 API 호출량이 캐시로 억제되어 요금이 예측 가능합니다. 호환 착오로 인한 반품·교환 문의가 줄어드는 것이 이 프로젝트의 실질 성과라고 봅니다.

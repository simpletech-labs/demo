지원 내용 (본문)

<프로젝트 진단>
공고에 범위가 이미 좁게 정해져 있습니다. 화면 개발은 제외, 데이터베이스와 REST API 서버만, 2~3주, 전부 원격. 이 조건에서 결과물의 품질을 가르는 것은 코드 양이 아니라 ① 테이블 설계를 화면이 아니라 업무 규칙 기준으로 잡는 것 ② API 계약(요청·응답·에러 코드)을 문서로 남겨 프론트 작업자가 기다리지 않게 하는 것입니다.
21일은 15영업일이고, 원격 진행이라 미팅은 정해진 시간에만 합니다. 15영업일입니다. 설계·구현·검수에 각각 시간을 배분하면 실질 구현은 9일 남짓이므로, 이 기간에 맞는 범위를 먼저 확정하는 것이 이 견적의 전제입니다. 엔티티 8~10개, 인증 포함 API 30개 내외를 기준으로 잡았습니다.

<작업 범위>
진행할 범위
1. 데이터 모델링 — 기존 화면·기획 자료를 읽고 엔티티와 관계를 정리한 ERD, 마이그레이션 파일.
2. DB 구축 — 개발·운영 스키마 분리, 인덱스, 제약조건, 시드 데이터.
3. REST API — 목록·상세·생성·수정·삭제, 페이지네이션·정렬·검색, 입력 검증, 공통 에러 형식.
4. 인증·권한 — 토큰 기반 로그인, 역할별 접근 제어, 비밀번호 해시.
5. 문서 — OpenAPI(Swagger) 자동 문서, 프론트 작업자를 위한 호출 예시, 로컬 실행 방법.
6. 배포 — Docker 구성, 환경변수 분리, 스테이징 배포와 헬스체크.

제외할 범위
프론트엔드 화면 개발, 디자인, 서버 인프라 구축·비용(호스팅 계정은 클라이언트 제공), 외부 결제·문자·알림 연동, 앱스토어 배포.

추가로 제안하는 범위
관리자용 통계 API와 배치 작업(정산·알림 발송). 21일 일정에는 넣지 않았고, 필요하면 일정과 금액을 다시 짜서 함께 진행합니다.

<리스크와 대응>
가장 먼저 확인할 것은 기획 자료의 완성도입니다. 화면 정의서나 데이터 항목 정의가 없으면 ERD를 두 번 그리게 되고, 그만큼 구현 일수가 줄어듭니다. 착수 첫날 자료 목록을 확인하고, 부족한 항목은 D3까지 질문 목록으로 정리해 확정합니다.
두 번째는 범위 증가입니다. 21일에 API 30개 내외가 기준이고, 엔티티가 늘면 같은 기간에 API 수를 줄이거나 기간을 늘려야 합니다. 추가분은 착수 전에 목록으로 합의하고, 같은 기간에 넣을 수 없는 항목은 2차로 분리합니다.
세 번째는 기존 코드와의 충돌입니다. 이미 개발 중인 플랫폼이라면 사용 중인 DB·프레임워크·인증 방식이 있습니다. 같은 스택을 따르는 것을 원칙으로 하고, 다를 경우 이유와 비용을 먼저 말씀드립니다.
네 번째는 운영 환경입니다. 호스팅·도메인·SSL은 클라이언트 제공이 전제이며, 제공이 늦어지면 스테이징 배포 일정이 밀립니다.

<기대 결과>
21일 뒤에는 프론트 작업자가 문서만 보고 API를 붙일 수 있는 상태가 됩니다. ERD·마이그레이션·OpenAPI 문서·로컬 실행 안내가 함께 넘어가고, 스테이징에 올라간 서버에서 실제 호출로 확인이 끝난 상태입니다. 이후 화면 개발은 API를 기다리지 않고 진행할 수 있고, 유지보수를 다른 사람이 맡아도 문서만으로 이어받을 수 있습니다.
